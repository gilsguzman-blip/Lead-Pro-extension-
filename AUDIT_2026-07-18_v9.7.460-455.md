## C. Confirmed Fixes (made this session)

**I1 — Appointment Invite UTC date shift.**
- **What changed:** `_lpInviteFormatDate()` — replaced `d.toISOString().split('T')[0]` (UTC) with local `getFullYear()/getMonth()/getDate()` formatting, matching the local-time frame `_lpInviteFormatTime()` already uses. One function; invite tab only; grab path, generation, and scraper untouched (`scraperVersion` stays v9.7.51).
- **Why:** any appointment at/after 7:00 PM CDT (6:00 PM CST) crossed UTC midnight, so the invite's date field — and the .ics emailed to the customer — carried the **next** day. Reproduced before fixing; re-verified after: `7/20/26 7:00p → 2026-07-20`, `1/20/26 6:00p → 2026-01-20`, 1:30p control unchanged, null-guard intact, in both CDT and CST.
- **Diff (identical in both builds, modulo the version number in the comment):**
```diff
-function _lpInviteFormatDate(d) { return d ? d.toISOString().split('T')[0] : ''; }
+// (v9.7.461/456 fix) LOCAL date, never toISOString — toISOString converts to UTC, so any
+// appointment at/after 7:00 PM CDT (6:00 PM CST) crossed UTC midnight and filled the
+// date field one day LATE while the time field (toTimeString, local) stayed correct. ...
+function _lpInviteFormatDate(d) {
+  if (!d) return '';
+  return d.getFullYear() + '-' + String(d.getMonth() + 1).padStart(2, '0') + '-' + String(d.getDate()).padStart(2, '0');
+}
```
- **Both builds, versions bumped, changelog convention matched:** DEV → **v9.7.461-dev** (manifest 9.7.461 / `9.7.461-dev`), COMMERCIAL → **v9.7.456** (manifest 9.7.456).
